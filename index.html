2. Skema SQL Supabase PostgreSQL

Contoh skema inti. Jalankan melalui Supabase SQL Editor setelah ditinjau dan disesuaikan dengan kebijakan akuntansi organisasi.

create extension if not exists pgcrypto;

create table public.chart_of_accounts (
  id uuid primary key default gen_random_uuid(),
  account_code text not null unique,
  account_name text not null,
  account_type text not null check
    (account_type in ('ASSET','LIABILITY','EQUITY','REVENUE','EXPENSE')),
  is_active boolean not null default true,
  created_at timestamptz not null default now()
);

create table public.journal_headers (
  id uuid primary key default gen_random_uuid(),
  voucher_number text not null unique,
  transaction_date date not null,
  description text not null check (length(trim(description)) > 0),
  transaction_type text not null default 'CASH_DISBURSEMENT'
    check (transaction_type = 'CASH_DISBURSEMENT'),
  status text not null default 'DRAFT'
    check (status in ('DRAFT','POSTED','REVERSED')),
  created_by uuid not null references auth.users(id),
  created_at timestamptz not null default now(),
  posted_by uuid references auth.users(id),
  posted_at timestamptz,
  hash_checksum text,
  reversed_journal_id uuid references public.journal_headers(id),
  updated_at timestamptz not null default now()
);

create table public.journal_lines (
  id uuid primary key default gen_random_uuid(),
  journal_id uuid not null references public.journal_headers(id)
    on delete restrict,
  line_no integer not null check (line_no > 0),
  account_id uuid not null references public.chart_of_accounts(id),
  debit numeric(20,2) not null default 0 check (debit >= 0),
  credit numeric(20,2) not null default 0 check (credit >= 0),
  created_at timestamptz not null default now(),
  unique (journal_id, line_no),
  check (
    (debit > 0 and credit = 0) or
    (credit > 0 and debit = 0)
  )
);

create table public.audit_logs (
  id bigint generated always as identity primary key,
  actor_id uuid references auth.users(id),
  action text not null,
  entity_type text not null,
  entity_id uuid,
  occurred_at timestamptz not null default now(),
  request_id text,
  old_data jsonb,
  new_data jsonb,
  metadata jsonb not null default '{}'::jsonb
);

create index journal_headers_date_idx
  on public.journal_headers(transaction_date);
create index journal_headers_status_idx
  on public.journal_headers(status);
create index journal_lines_journal_idx
  on public.journal_lines(journal_id);
create index audit_logs_entity_idx
  on public.audit_logs(entity_type, entity_id, occurred_at desc);

Catatan: foreign key reversed_journal_id menghubungkan jurnal yang dikoreksi ke jurnal pembalik; pertimbangkan unique constraint parsial agar satu jurnal tidak dibalik berkali-kali.

3. Hash checksum dan audit trail
  • created_by diambil dari identitas terautentikasi server, misalnya auth.uid(); jangan menerima nilai ini begitu saja dari request browser.
  • created_at dibuat oleh database dengan now() dalam timestamptz.
  • hash_checksum dihitung di sisi server dari representasi kanonis header dan seluruh baris yang diurutkan menurut line_no. Gunakan format serialisasi deterministik dan SHA-256 (misalnya pgcrypto.digest(..., 'sha256')).
  • Sertakan voucher, tanggal, deskripsi, akun, debit, kredit, dan identitas versi skema dalam payload hash. Simpan hasil sebagai hex.
  • Checksum membantu mendeteksi perubahan, tetapi bukan pengganti kontrol akses, audit log append-only, atau tanda tangan digital. Jika penyerang dapat mengubah data sekaligus hash, hash biasa saja tidak cukup.
  • Audit log dicatat di transaksi database yang sama dengan perubahan jurnal. Batasi UPDATE/DELETE pada audit log melalui privilege dan trigger/policy.
4. Aturan validasi backend sebelum simpan/posting
  1. Validasi sesi pengguna dan otorisasi peran; identitas created_by harus berasal dari sesi terpercaya.
  2. Validasi tanggal, nomor voucher, deskripsi, jumlah baris minimal dua, akun aktif dan dapat diposting, serta format nominal presisi dua desimal.
  3. Untuk setiap baris, debit dan kredit tidak boleh negatif; tepat satu sisi harus positif. Tolak baris dengan keduanya nol atau keduanya positif.
  4. Hitung ulang total debit dan kredit di server menggunakan numeric; wajib sama persis. Jangan percaya total yang dikirim browser.
  5. Simpan header dan lines secara atomik dalam satu transaksi/RPC. Terapkan unique constraint nomor voucher untuk mencegah duplikasi/race condition.
  6. Saat posting, lock header dengan SELECT ... FOR UPDATE, pastikan status masih DRAFT, validasi ulang seluruh baris, lalu set POSTED, posted_by, posted_at, dan checksum.
  7. Blokir perubahan atau penghapusan langsung atas header/lines berstatus POSTED melalui RPC, trigger, dan privilege database. RLS saja tidak menggantikan aturan bisnis ini.
  8. Koreksi dilakukan dengan membuat jurnal pembalik baru: nilai debit/kredit dibalik, referensi jurnal asal dicatat, dan keduanya terhubung lewat audit log. Jangan mengedit jurnal posted untuk “memperbaikinya”.

Contoh guard trigger untuk jurnal POSTED

Trigger ini adalah lapisan perlindungan tambahan; buat fungsi serupa untuk journal_lines yang memeriksa status header induk. Tetap batasi hak akses tabel dan arahkan perubahan melalui RPC tepercaya.

create or replace function public.prevent_posted_header_mutation()
returns trigger
language plpgsql
as $$
begin
  if old.status = 'POSTED' then
    raise exception 'Jurnal POSTED tidak boleh diubah atau dihapus; buat jurnal pembalik.';
  end if;
  return coalesce(new, old);
end;
$$;

create trigger journal_header_posted_guard
before update or delete on public.journal_headers
for each row execute function public.prevent_posted_header_mutation();

Implementasi produksi perlu mengizinkan transisi status yang dirancang secara eksplisit, misalnya POSTED → REVERSED hanya melalui fungsi reversal terotorisasi; trigger contoh di atas sengaja konservatif dan akan memblokir transisi tersebut sampai fungsi/aturan khusus dibuat.

5. Konfigurasi Supabase

  1. Buat proyek Supabase dan jalankan migrasi SQL yang sudah direview.
  2. Aktifkan Authentication dan siapkan peran pengguna, misalnya pembuat, reviewer, dan poster.
  3. Aktifkan RLS pada tabel yang diakses melalui API. Buat policy least-privilege untuk SELECT dan operasi yang memang diizinkan.
  4. Gunakan Supabase client di frontend dengan Project URL dan anon/publishable key. Key ini boleh ada di frontend jika RLS benar; jangan pernah mengekspos service-role key.
  5. Untuk simpan/posting, panggil PostgreSQL RPC atau Edge Function yang memvalidasi dan menulis data secara atomik. Jangan memberi browser akses bebas untuk mengubah status POSTED.
npm install @supabase/supabase-js
